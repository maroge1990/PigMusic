Durable facts: the product contract, current state, the one roadmap, decisions and architecture. How to build, test and ship is in [AGENTS.md](AGENTS.md); operations in [docs/operations.md](docs/operations.md). Delivery history is in git (`git log`), not here. Update the current-state and roadmap sections when a delivery lands. Say whether each item is **delivered**, **in progress**, **planned** or **unverified**.

## Product contract

PigMusic is a private household music-library manager with one container, one interface, shared settings and one persistent download queue. It replaces the household's Lidarr, Soularr, Music Grabber and separate slskd containers. The slskd engine stays embedded inside PigMusic. Plex reads the same Synology files.

- Phone use should be quick: find an artist, see what is saved and what is available, then request an artist, album or song without choosing a backend. Desktop supports investigation and troubleshooting. Keep technical options in Settings or collapsed disclosures; ask the owner before adding nonessential main-interface controls.
- A song is the same song on any edition of any album. One compatibility policy (`matching.compatible`: lead artist, edition-free title, recording kind, agreeing known recording IDs and lengths) serves library matching, queue deduplication, duplicate detection and source selection. A request (playlist import, search, mix, album) is satisfied by the household's copy wherever it sits; a missing song is downloaded from any edition's source and filed and tagged, with its cover, by known identity first: a requested release keeps its release group and moves only to that group's recommended edition holding the same recording; a requested recording is filed under the best album holding it; a request with neither goes to the artist's own studio album containing the song, on its recommended edition. Live, remix, acoustic, demo and similar recordings stay distinct (by title, album title or release type: `recording_kind`, carried from the catalogue release through presence, lookup and requests), and the original request is kept apart from the filing (`requested`). The only exception is an edition chosen explicitly from "Other versions" (`explicit_edition`): it keeps that exact release, and conflicting known release or recording IDs never become a confident match there. Uncertain or ambiguous matches require review.
- Each person has their own library memberships over shared files. One exact file may back several memberships and is stored once. Removing a membership keeps files that are still needed elsewhere.
- Quality defaults apply system → artist → album, with album the most specific. Explicit upgrades **and downgrades acquire new source files**; never transcode to reach a target quality. Validate the replacement before retiring the existing file. Fallback order:
  1. preferred quality;
  2. MP3;
  3. AAC 256 kbps (lowest rank). AAC is used only when JioSaavn is an enabled source, only for requests made after this fallback was added, and never when the owner chooses to wait for lossless.

  Lower-quality saves are re-checked every `recheck_hours`. Upgrade jobs never fall back, and automatic improvements never downgrade.
- Import is reviewed before acquisition. An Apple XML playlist becomes a persistent ordered playlist. Available files play immediately; missing files join after acquisition. Importing an inventory must not download everything.
- Favourites are a special playlist and membership only. Starring a missing song never submits a download.
- Personalised mixes blend existing household files with discoveries downloaded ahead of playback into a managed server cache. This authorises temporary mix preparation, not automatic library membership or NAS publication. Retire cached discoveries when no active mix or playback needs them; explicitly added library songs must remain available independently of cache cleanup. It is on `main`, not yet released.
- Existing music can be scanned without modification. Naming/tagging changes need a concrete review, recoverable originals and hash/path guards. Never bulk-reorganise music as a side effect of a code migration.
- Only multi-artist compilations are separated; a single artist's greatest hits stays with that artist. Soundtracks and musicals get their own sections. Empty section headings stay hidden.
- Internet access uses one public HTTPS origin (`https://music.markrogers.au` via Cloudflare Tunnel), gated only by PigMusic accounts. Tailscale remains the owner's administration route. People join only by a one-use invite link or QR code, never an external allowlist. See [internet access](docs/internet-access.md). Secrets stay server-side and never enter Git, bundles, logs, browser responses or docs.
- Fanart and ListenBrainz are optional. Without a key or token, their artist enhancements disappear quietly. Remote playback is experimental and provider-dependent; it never adds a file to the library. Household files play for every member without being added.
- The owner sees the member experience plus an Admin section, with admin options always at the bottom of shared views. Administration stays web-only.

## Decisions

- **Phase 1 (Oct 2026):** One app owns orchestration and publication, with slskd embedded and upstream parsers reused under `server/vendor/` (licences retained). Never recreate separate managers.
- **Identity:** Compilation, live and request context take precedence. Identical copies may serve several places but are stored once.
- **Quality:** No conversion. System defaults with artist/album overrides in both directions; acquire and validate a new source, then retire the old file.
- **Playlists:** Available songs play immediately and missing ones join as they arrive. PigMusic keeps every ordered occurrence.
- **6 Oct:** Docs consolidate into this blueprint as the single roadmap. GHCR (`ghcr.io/maroge1990/pig-music`, private) is the release channel for the existing Unraid server.
- **7 Oct:** Accounts with personal libraries; owner bootstrap through the first-run WebUI with a console installation code. Docker Manager (`unraid/PigMusic.xml`) is the only management source; Compose is retired.
- **9 Oct:** Internet via Cloudflare Tunnel gated by PigMusic accounts, not Cloudflare Access (a second guest list that would block the native app). Two artist pages: library = play what you have, catalogue = find what you could have. Members keep their own quality. Recommendations sit above popularity. Popular in Australia comes from Apple only. ListenBrainz is kept only for LB Radio similarity and per-artist popularity. A one-time owner choice is acceptable for ambiguous artists.
- **11 Oct:** All seven acquisition sources are implemented. Existing source lists and defaults are unchanged.
- **12 Oct:** Layout: integrated phone player/tab dock, settings below the music on detail pages, compact headers, and Home without song recommendations (web and native). Watch music lives on the Watch, prepared by the paired phone; the Watch never receives server credentials.

- **14 Oct:** Search artist results open the full artist page, which links to the library page. Household files play for any member without being added first; adding still creates a library membership. A device download that belongs to both an album and a playlist shows under both, and the file stays on the device until both are removed. Playlists sent to the Watch update automatically. Remote playback never streams lossless, even on Wi-Fi; MP3 sources come first.
- **16 Oct, mix scope:** Discovered songs in personalised mixes are downloaded in advance to a managed server cache using the download pipeline, then played from PigMusic. Once no rotating mix or active playback needs a file, it can be removed unless it has been explicitly retained in a library. This is separate from the existing experimental remote-playback policy; cache preparation does not create library memberships.
- **17 Oct, more discovery and radio:** Storage is plentiful, so mixes lean on discovery: five new mix kinds, a larger daily discovery pool and an endless personal radio. Continuous radio moves out of "later scope". Forgotten favourites waits until there is listening history; Back in the mix stays a library shuffle.
- **19 Oct, mix size and Home albums:** A 5-song mix is a poor experience, so 20 songs is the minimum, topped up from the library where it fits. Home catalogue albums are pre-cached (server warmer and the phone) so they open like library albums. The iPhone no longer shows sync errors when it falls back to the cached library. Playlists offer adding missing songs to the server from the download button, separately from device downloads.
- **22 Oct, editions and order:** A deluxe or remastered edition is not a new album; a single or EP, a live album and a greatest hits are. Tidying keeps the fullest edition with the better copy of each song moved into it. The next release waits for TIDY. SPLIT waits for V01; the Mac app and Shazam are deferred indefinitely.
- **17 Oct:** Plex integration is retired. PigMusic's own web, iPhone and Watch players replace Plex playlist export and per-person Plex tokens; migration 11 drops the token table and sync state. The trash folder keeps its `.plexignore` so a Plex server indexing the same share still skips it.

## Discovery and recognition scope

Scope researched 16 October 2026. Advance caching, Pig-Branding-based draft artwork and one horizontal row are owner-selected. This has not been deployed, and real-source/device acceptance remains open.

### Product direction

Personalised mixes become the principal reason to open PigMusic: familiar music, rediscovery and relevant discoveries, presented as a small set of inviting listening choices. The library is a taste signal, not the boundary of discovery. Household availability is a playback advantage, not evidence that another member's tastes belong to this person.

Working naming: **Your mixes** for the Home shelf and **Daily blend** for its lead mix. Artist/genre cards get concrete names such as **Around Radiohead** and **Indie rotation**. Alternatives: **Made for you** (clear but generic), **Daily picks** (suggests individual recommendations), **Pig Radio** (better reserved for a future continuous station). Avoid promising a different mood from the clock alone, or labelling rule-based selection as AI.

Home order on web and iOS: Your mixes, Recently added, Recommended artists/albums, Popular. Lead with one prominent mix and a compact row of other themes; avoid a full-screen hero that hides everything else. Cards show a title, artwork, a few representative artists, a short reason and Play. Opening a card shows its ordered songs, availability, edition date and save action. No recommended-song feed is added to Home; songs live inside mixes. Existing artist/album recommendations may use the same candidate engine later, rather than maintaining competing recommendation logic.

Initial mix families (about four to six cards, only when there is enough material):

| Mix | Listening intent | Initial composition hypothesis |
| --- | --- | --- |
| Daily blend | The easiest first play | 60% personal-library music, 30% related discoveries, 10% relevant current-chart discoveries |
| Genre rotation | A genre this person actually likes | Familiar anchors and related discoveries within a supported genre |
| Around an artist | One artist and their musical neighbourhood | Seed artist plus related artists; clearly distinct from an artist-only playlist |
| In rotation | Popular now, filtered for this person's taste | Current regional chart candidates ranked by affinity; hide when there is no convincing fit |
| Back in the mix | Rediscover saved music | Personal-library tracks not heard recently; no discovery quota |

Percentages are experiment settings, not a universal recipe. Buckets must be disjoint for allocation: an owned chart song counts as owned, and a chart discovery is not also counted as a related discovery. Ownership is not familiarity: distinguish unheard library tracks, recently played favourites, neglected songs and new-to-Pig discoveries. Imported inventories are weaker evidence than listening and favourites; cap per-artist influence so a large discography cannot dominate.

### What existing products teach us

Spotify describes Daily Mix as distinct taste groupings weighted toward familiar music, with gentler discovery than Discover Weekly. The useful lesson is separate listening intents, rather than giving every playlist the same novelty ratio. Its [Daily Mix explanation](https://newsroom.spotify.com/2018-05-18/how-your-daily-mix-just-gets-you/) is a published design description, not disclosure of today's complete ranking algorithm.

[Spotify daylist](https://newsroom.spotify.com/2023-09-12/ever-changing-playlist-daylist-music-for-all-day/) changes its selection and presentation during the day. PigMusic should borrow the sense of a timely edition while keeping a playing queue stable. [YouTube Music's tuner](https://blog.youtube/news-and-events/get-started-youtube-music/) separates artist seeds, familiarity, variety and popularity/new-release filters. Those are useful independent controls inside the engine even if the first UI exposes very few. Apple's [Discovery Station](https://itunespartner.apple.com/music/support/5384-discovery-station-streams-container-sub-type) explicitly targets songs outside a subscriber's listening, playlists and library: a useful model for a later dedicated discovery mix, distinct from the welcoming daily blend.

Inference from these product descriptions: freshness comes from choosing a relevant listening context, varying exposure and balancing familiarity with novelty. Random shuffling and renaming the same tracks will not achieve that. These sources do not establish optimal ratios for this household.

### Data services and replacement options

PigMusic should own personal ranking, mixing, sequencing and freshness. Providers supply candidate recordings, relationships, tags and popularity. A service that generates playlists still needs local-library matching, per-person policy and availability handling.

| ListenBrainz / Troi | Artist-seeded recordings, genre/tag recordings and popularity; Troi offers weighted radio terms and local/global playlist generation | First benchmark candidate. | Last.fm | Track/artist similarity, tag charts, artist tracks and global/country popularity via an API key | Strong challenger: could replace ListenBrainz recommendation/popularity lookups if coverage and quality win. Do not add providers merely to collect more results. A winner may replace the existing recommendation provider; replace the chart source too only if it demonstrates the required regional freshness. Keep provider outputs behind a shared candidate interface so either decision is reversible.

Further MX0 comparisons should use synthetic/curated seeds spanning mainstream, niche, older, Australian and non-English music, with sparse and large-library scenarios. No real household history is uploaded. Compare identity-match coverage, ambiguous/wrong versions, distinct relevant candidates per seed, genre coherence, current-chart overlap/freshness, response latency, throttling, setup burden and usable playback availability. API documentation alone is not evidence that a new key works or the results sound good. Include a small listening review against library shuffle and today's recommendation feed. Record attribution/caching requirements before choosing a replacement integration.

The bounded live baseline probe returned 28–32 distinct recording MBIDs across 7–8 artists for each of Radiohead, The Beatles and AC/DC in 0.54–1.23 seconds. Apple's Australian chart returned 25 entries in 2.25 seconds. Broad rock/jazz tag requests timed out at six seconds; a smaller, explicit-operator indie-rock request succeeded in 3.37 seconds. The generator now requests only the six tag candidates it consumes and keeps its bounded timeout/fallback behavior. These probes establish reachability and response shape, not listening quality or non-English coverage. No Last.fm key or Apple developer token was configured.

An isolated real-source acceptance used [Scott Buckley's CC-BY recording Signal to Noise](https://www.scottbuckley.com.au/library/signal-to-noise/). The source-native AAC original measured 128 kbps, 353.50 seconds and 5,723,611 bytes; search, transfer, full validation and fresh-state cache verification completed in 17.16 seconds. Unreferenced cleanup passed and no queue, acquired or library-membership rows were created. The test also exposed a shared pipeline issue: some AAC MP4s omit nominal bitrate. The reader now measures audio-packet bytes, as it already did for Opus/Vorbis, without changing audio or weakening quality thresholds. This is one native-quality sample, not evidence of all-source/default-320-kbps success or household-wide cache sizing.

### Freshness, personalisation and playback

Start with deterministic, versioned daily editions per person and configured timezone. Both clients show the same edition. Refreshing Home does not reshuffle it; new feedback shapes the next edition, while a hide can take effect immediately. Freeze a playing queue and any saved edition. Time-of-day variants come later if actual listening supports them.

Rotate the featured theme, opening songs, candidate seeds and neglected library material. Starting experiment targets for a sufficiently large pool: 25–40 songs per edition, at least half the daily blend changed from yesterday, no recording duplicated within a mix, no adjacent tracks by the same artist, normally at most two tracks per artist. Reduce repeated exposure across Home cards and penalise recently heard tracks. Preserve requested live/remix/edition identity when resolving and deduplicating. Relax freshness targets for small libraries. Every rotating mix has at least **20 songs**: where it fits the theme it is topped up from the person's own library; otherwise it is not shown. Distinguish new releases from old songs newly discovered by this person, and current chart evidence from lifetime popularity.

The first release ranks from library artists/genres and explicit favourites/hides, while avoiding recently qualified listens and yesterday's Daily blend exposure. Genre themes rotate across the top three genres by distinct artists, so one large discography cannot dominate. Daily blends backfill with relevant library music when discovery supply is sparse; the standalone popularity mix has its own size rather than the daily chart allowance. Artist neighbourhood mixes require more than one artist and top up with the artist's other songs, then owned songs by neighbouring artists, then owned songs in the artist's main genre. Genre and decade mixes top up from owned songs in that genre or decade. Discovery-only mixes (Fresh finds, New from your artists, In rotation) and library-only mixes are not topped up and are skipped below 20. Longer-term affinity weighting, personal-playlist-addition signals, deliberate-skip feedback and an exploration control are later tuning work. Skips must never equate network errors or interruptions with dislike.

Cold start uses imported/saved library metadata even when its files are not yet available. With no taste seeds, prepare clearly labelled regional popularity rather than pretending it is personalised. Artist/genre onboarding choices can follow later. Provider failures retain usable ready editions and local rediscovery while replacements prepare. Cached native Home remains useful offline, but only tracks downloaded onto the device are playable offline. Keep personal ranking/history local to PigMusic; external seed queries still reveal queried artists/tags. Do not submit listening histories or require each member to create a discovery-provider account.

**Chosen playback policy: prepare discoveries before playback.** Mixes blend existing household files with discovered songs fully downloaded and validated in a managed server cache. Use the normal download pipeline's supported sources, identity checks, validation and retry/fallback rules with an explicit temporary-cache destination/purpose. This requires adapting its publication boundary: preparation must not publish into the NAS, add library membership, trigger library scanning or create library quality-upgrade jobs. Cache quality needs a bounded policy established during MX0; do not assume the existing lossy remote-streaming policy or automatic lossless acquisition. Never transcode to meet a quality target. Cache files play from PigMusic on web and iOS, with no dependency on a third-party stream starting when Play is pressed. Server caching still requires connectivity from the player; phone offline availability remains an explicit device-download flow.

### Mix preparation and cache lifecycle

- Generate and prepare forthcoming editions in the background, ahead of the daily rotation. Reuse a suitable exact household file first; deduplicate matching cache files and in-flight transfers across editions and members without sharing personal ranking/history. Cache references preserve recording and edition identity. Cache capacity supports a substantial rotation, not merely the next two songs in a queue.
- Stage a new edition while its discoveries download. A mix advertised as ready must have every queued song backed by a validated household/cache file. Keep the previous ready edition until the replacement is ready. On a first preparation, show a simple preparing state and an immediately playable library mix. Within a bounded preparation window, replace failed candidates with the edition's planned library backfill, or retire the edition if it cannot reach 20 songs (Home also hides any older edition under 20); do not conceal missing songs behind a ready label. Once published, freeze that edition's tracklist. Retain failed-candidate diagnostics for the owner.
- Persist file/edition references, preparation state and retry scheduling so restarts do not restart all work. Bound transfer concurrency and prioritise current/next editions; explicit library requests and playback must not be starved by speculative preparation. Loading Home reads prepared state and does not enqueue duplicate downloads on each visit.
- An active rotating mix retains its cached songs even if nobody has played them recently. When an edition leaves rotation, release its references. Delete an unretained cache file only after checking all members' active editions, active/paused queue leases and in-flight library promotion. Use a bounded, renewable playback lease plus a short cleanup grace period; abandoned queues must not pin files forever. Cleanup is reference-based, restart-safe and cannot remove NAS/library files.
- **Add to library** makes the song durable independently of the mix. Reuse/promote the validated cache file if it satisfies the person's quality and edition requirements, using the normal safe publication path; otherwise acquire the required file and retain the playable cache copy until publication succeeds. Adding another member's already published exact song creates membership over the shared file. Failures leave the cache reference protected and report a pending/failed library addition. Favouriting alone keeps its existing membership-only semantics and does not cause acquisition.
- Saving a mix preserves its ordered playlist metadata. It does not permanently retain every discovery's audio or add those songs to the library. Explain that distinction when saving; after rotation, songs not added to the library can require preparation again on the next play. Explicit device downloads require the existing library/device-copy rules. Long-term Watch availability requires eligible durable songs.
- Use a dedicated configurable server-cache budget and disk-free reserve, reported in web Admin with preparing/ready/failed counts and reclaimable bytes. The existing remote cache's 5 GB / 14-day least-recently-played policy is insufficient: it can evict an unplayed song still needed by an active mix. If a shared physical cache is used, every eviction path must respect mix and playback references. Reclaim unreferenced files first; if capacity is still insufficient, pause/defer preparation or reduce future mix size/count explicitly rather than evict ready songs. Do not check or assume real NAS free space as part of scoping.

Sizing illustration, not a quota or measured household requirement: a four-minute song at 320 kbps is about 9.6 MB. One hundred 40-song mixes with 40% discoveries need about 15.4 GB for discovery audio before deduplication; if all songs need caching, about 38.4 GB. Allow additional capacity for overlapping old/new editions, playback leases, temporary transfers and the disk reserve. Lossless and longer tracks can change this substantially. MX0 must measure expected duration/format, distinct discoveries, household reuse and rotation overlap before choosing a default; do not assume compression by transcoding.

Automatic mix preparation is explicitly authorised by this product decision. It must remain separate from imports, favourites and library acquisition. Continuous radio and automatic phone/Watch downloads remain outside MX2.

### Implementation boundaries and acceptance

Current implementation: `server/mixes.py` owns private daily editions and uses `server/home.py` for bounded LB Radio artist/tag candidates and the existing Apple public regional chart. `server/mix_cache.py` reuses the standard downloader's identity, transfer and validation pipeline with a temporary publication boundary. Work has a four-minute per-person pass budget, persisted song cursors and retry scheduling; a shared transfer lock prevents duplicate on-demand/automatic downloads. Web and iOS lead with mixes. Signed mix aliases authorise ready audio and qualified history without library membership; saved-edition playback can prepare a fresh temporary lease even when experimental streaming is disabled. Native playback retains the returned history identity for these listens. Owner diagnostics report genuine candidate failures, paused/capacity reasons and reclaimable bytes, plus a per-person view of every live edition's intended songs and each song's state (library, cached, up next, waiting, unavailable with reason, left out, hidden). Publishes and unavailable songs are logged at INFO.

MX1 adds provider-neutral candidates, a versioned generator, persisted per-person mix definitions/editions, durable preparation jobs, cache references/leases, safe library promotion, feedback/exposure records and recording-aware history for authorised playback outside personal membership. Shared public candidate caches must remain separate from private rankings and feedback. Generate and download off the request path with bounded work, provider backoff and last-good results; respect the container's 1 GB verification gate. Refresh a prepared edition atomically. An authenticated mixes API returns stable definition/edition/entry identities, reasons, timestamps, attribution and preparation/availability state; playback authorisation must recognise active mix/cache entitlement without requiring personal library membership or exposing raw paths. Extend OpenAPI and PigKit together.

MX2 renders the same prepared editions in both clients and integrates normal playback and Add to library controls. Saving makes an ordinary persistent playlist snapshot; a later mix refresh cannot rewrite it. Apply the cache-retention distinction above and existing Watch flows for eligible durable songs, with no new automatic device following/download behaviour. Custom user-authored rule builders, language prompts, mood/tempo inference, radio seeded from any song or artist and direct dynamic Watch mixes are later scope. The personal radio (MX4) is in scope.

Acceptance gates: reproducible editions across clients; meaningful day-to-day change where the pool permits; no cross-member taste/history leaks; exact identity retained; preparation creates no library memberships or NAS publication; ready mixes play entirely from validated files; honest sparse-library/provider-outage states; saves and active queues survive refresh; discovery listens influence subsequent editions; explicit hides persist; plausible theme and artist diversity. Exercise shared-file references, rotation during playback, cache exhaustion, interrupted transfers/restarts and cleanup concurrent with Add to library. Retiring one member's mix must not delete audio another active mix needs; removing cached audio must never remove a library file. Measure play starts, deliberate skips, discovery saves, repeat exposure, cache hit rate/bytes, preparation completion/failure and cached playback start latency locally. Validate perceived freshness and listening coherence with the owner across several daily editions before calling the feature successful. Coverage and latency thresholds are set from MX0, not invented from documentation.

### Shazam: optional capture, then recognition

The useful goal is to carry a song found elsewhere into a private **song inbox**, where it can be matched, played if available, saved or explicitly requested. Capture is weak interest evidence, not a favourite or permission to download. The inbox syncs to web even if the capture entry point is iOS-only.

There are three distinct routes:

1. **Share from Shazam to PigMusic:** Apple documents [sharing identified songs to other apps](https://support.apple.com/en-qa/guide/shazam/deva91f77c6a/1.0/web/1.0). A PigMusic share extension is the first feasibility candidate. Prove the actual URL/text payload, supported metadata resolution, signed-in account handling and offline handoff on a device. Preserve an unresolved inbox item if identity cannot be confirmed; do not scrape Shazam HTML or guess an edition. If the supported payload cannot be resolved cleanly, abandon this route. It is not established merely because the share sheet exists.
2. **Recognise inside PigMusic:** [ShazamKit](https://developer.apple.com/shazamkit/) is Apple's supported recognition framework. A small foreground microphone flow can identify a song and offer to save it to the same inbox. Apple's [setup instructions](https://developer.apple.com/help/account/services/shazamkit) require enabling the ShazamKit service for the App ID. Prove entitlement/provisioning with this project's current Personal Team before scheduling it; availability with that signing setup is unverified. Include microphone denial, no match, cancellation, network failure and audio-session recovery. No always-listening/background capture or web recognition in this scope.
3. **Import all existing Shazams:** not available directly through ShazamKit. Apple's [WWDC explanation of SHLibrary](https://developer.apple.com/videos/play/wwdc2023/10051/) states that reads/deletes cover only items added by the calling app. Apple documents an [Apple Music “My Shazam Tracks” sync route](https://support.apple.com/en-gb/guide/shazam/dev64d8cd51e/web), but importing that playlist adds account/subscription/authorisation dependencies. Defer unless an owner explicitly wants that bridge.

S01 is a short, bounded feasibility spike and, if successful, share-to-inbox. S02 is separately optional in-app recognition, only after real-device provisioning works. Neither is a prerequisite for mixes. Stop if the supported handoff is fragile or recognition needs an account/signing commitment the owner does not want. Do not build a generic import framework to rescue this nice-to-have.

## Architecture

SQLite owns the durable queue, acquired records, playlists, preferences, accounts and metadata documents. Appdata holds the snapshot, private connection files, artwork and operation journals. **Identity invariants:**
- Snapshot track IDs stay stable; acquired records supersede them for published replacements.
- Album edition anchors (`album-edition-anchors` document) keep the original album ID on its first known edition, so scan order cannot move links or preferences between editions. Unknown tags may join a sole known edition but never choose among several.
- Removal exclusions are edition-aware, and a restore clears only its own exclusions.
- Queue workers use claim tokens, so a cancelled or stale worker cannot publish into a reused request ID. Artist jobs use a separate generation guard.

Change none of these without migration fixtures and a backed-up production-state comparison.
